# Deployment and recovery

[English README](../README.md) · [中文说明](../README.zh-CN.md)

## Layout and configuration

The checkout and runtime are separate. Provision a new external runtime with `scripts/provision.py`; it copies the server and generic Skill, generates profiles and pins the actual mounted volume UUID. The script refuses a nonempty destination and does not modify an existing Worker. Examples under `config/` are deliberately nonfunctional placeholders, not credentials.

`Service/config/config.json` contains the deployment root/mount, volume UUID and owner marker, separate build/admin tokens, TLS files, listener and allowlist, selected Xcode developer directory, optional default simulator and disk admission/abort thresholds. Capacity thresholds use decimal GB. Tune them for your disk, leaving headroom for macOS and simulator boot. `allowed_networks` applies to the actual TCP peer; the service does not trust proxy headers.

The URL used during provisioning is placed in the certificate SAN and client profile. If the Mac's address or certificate changes, create and distribute an owner-verified replacement profile/pin. Certificates generated by the provisioner expire after 365 days. No trust store or TLS bypass is installed.

Keep these runtime directories external:

| Path | Purpose |
|---|---|
| Repos | Immutable source revisions |
| SourceStore | SHA-256 content objects |
| Workspaces | Stable per-project working copies |
| Caches | DerivedData, SourcePackages and PackageCache |
| Temporary | Per-job scratch space |
| Service/automation | Pinned UI controller checkout, build products and logs |
| Sessions | App stdout/stderr, controller logs and results |
| Results | Build products, xcresults, screenshots and diagnostic exports |
| Archives | Protected archive output |
| Simulators | Registered devices' data and logs |
| Client | Generated private client bundle; never publish |

## Register an existing device

Before any simulator work, inspect both `xcrun simctl list devices` and `xcrun simctl list devices booted`. A booted unreserved device is occupied; don't take it over. Read the project's device/runtime requirements.

Start the service, then invoke the generated Skill with a request file:

```json
{"operation":"simulators"}
```

Choose an existing idle compatible device from the actual inventory. Registration is an explicit provisioning change and uses the admin profile:

```json
{"operation":"register_device","simulator_id":"replace-with-existing-udid"}
```

The service copies the device data to the pinned volume, compares file hashes, symlink targets and directory structure, rechecks idle state, preserves the original as `data.before-ios-worker-v2`, then replaces `data` with a link to the external copy. Newly absent device log directories get an external link; preexisting log directories are left intact. No device/runtime is created and the original backup is not deleted.

Set `default_simulator` to the registered ID before the next service start, or specify the ID in requests. The API does not auto-select arbitrary devices when no default exists. Ordinary agents should reuse the registered pool rather than registering other projects' QA devices.

## Process lifetime and native launcher

`serve.py` acquires its single-instance lock before loading/recovering state. Duplicate startup must not interrupt the actual worker. Use one foreground server or one launcher, not multiple independent launchers.

The optional AppKit menu-bar app reads its root from its generated `Info.plist`. It restarts an exited child every 30 seconds, supports pause/resume, maintains a bounded server log and keeps the Mac awake while the child is running. Pausing stops the child; existing sessions become interrupted reservations. In a desktop login session it can obtain normal macOS removable-volume consent. It is not a root daemon, remote login mechanism or FileVault unlocker.

The build script writes the app to the external deployment and signs it ad hoc; it does not notarize or distribute a binary. Start it manually first. Login Items are an owner-managed choice.

## Updating and recovery

Wait for the queue and uploads to finish and close sessions before changing server files or controller builds. Back up `Service/config`, `Service/state` and source code privately. Preserve Archives and original simulator backups. This repository's provisioner is for a **new** deployment and is not an in-place updater.

On restart, unfinished jobs are marked interrupted rather than silently retried. Session reservations persist, preventing a different task from taking ownership. Inspect the interrupted session and explicitly close it before reopening. After an uncertain network POST, inspect recent jobs instead of blindly resubmitting.

A source-code rollback should preserve jobs created since the backup: do not overwrite the current state file without checking version compatibility and taking a current backup. Restoring a simulator data backup requires a shutdown device, verified destination and a separately reviewed operation; no automatic restore/delete is provided.

## Network and local execution

Use a reachable HTTPS origin and a narrow allowlist for trusted clients. A Skill is not a tunnel and cloud-hosted agents need their own authorized route. Raw UI-controller listeners stay on loopback; never expose them directly. Terminal/native-app external-volume permission and network reachability are independent checks.

`prepare_ui.py` downloads a fixed upstream commit without installing the Appium server. It can take several minutes and requires a compatible SDK. Ordinary builds do not require this controller. Logs are in `Service/automation/build.log`; preserve an existing modified checkout rather than resetting it automatically.

SwiftPM is supported. XcodeGen must already be installed when used. CocoaPods, Flutter/npm and other package systems require project-specific preparation. Signing identities, physical devices, Xcode Cloud and distribution accounts remain owner-managed.
